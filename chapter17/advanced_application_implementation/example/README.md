# 17. Advanced Application Implementation

A headless office pipeline that turns a vendor's structured data into a
**governed, watermarked, redacted and cryptographically signed PDF**, with
no Word or PDF application in sight. WordCraft composes the document;
PdfCraft governs it. Both are driven over MCP, so the whole pipeline runs
in a container with no GUI and no license server.

It is the reference implementation of the chapter's architecture: one
transport, one composer, one governor, one façade, one composition root.

## What it does

A tenant's DOCX template is merged with the vendor's data, exported to PDF,
and then put through a **fixed, ordered sequence of compliance passes**:

```
compose (WordCraft)  →  classify  →  watermark  →  redact  →  flatten
                      →  protect   →  sign       →  audit
```

The order is not decoration. Signing before mutation invalidates the seal,
and protecting before redaction hides the content the redactor is supposed
to find — so `nimbus-governor.ts` encodes the sequence as code and the
comments in that file say why each pass has to sit where it does.

Two documents come out: the signed edition, and a *governed but unsigned*
intermediate that every other artifact derives from. Every step is written
to an audit trail, and the pipeline's result carries the SHA-256 of the
bytes it actually wrote.

## The listings

| file | what it is |
| --- | --- |
| `office-bridge.ts` | the request contract, the shared types, and the MCP transport every other module goes through — it owns the stdio subprocesses, the capability gating and the retries |
| `nimbus-composer.ts` | the WordCraft half: template → merged DOCX → PDF. It knows how *this tenant's* template works and nothing about compliance. |
| `nimbus-governor.ts` | the PdfCraft half: the compliance policy, encoded as a fixed pass order |
| `nimbus-pipeline.ts` | the façade the SaaS layer calls — validation, the audit trail, the idempotency key |
| `nimbus-factory.ts` | the composition root: `createNimbusPipeline()` builds the whole graph and hands back a handle whose disposal tears both engines down |

## Run it

```bash
cd chapter17/advanced_application_implementation/example/files
export PATH="$PWD/../../../../tools/craft-cli/bin:$PATH"
npx tsx run_nimbus.ts
```

The pipeline runs for real: WordCraft merges a tenant template, PdfCraft
stamps the metadata, watermarks the pages, redacts the patterns, strips the
hidden information and signs the result. The harness then reads the
artifacts back and checks them.

```
PASS the tenant template was written
PASS the signing identity was created
PASS the pipeline reports one page
PASS the artefact is signed
PASS the audit event carries the tenant
PASS the audit event records the redaction
PASS the final PDF exists
PASS the reported hash is the hash of the bytes on disk
PASS the vendor name was merged
PASS the redacted phone number is gone
PASS the watermark was applied
PASS the payment schedule table was assembled
PASS the PDF carries one signature
PASS the PDF carries at least two revisions
...
25 assertions passed
```

## What it produces

Everything lands under `files/output/work/`:

| artifact | what it is |
| --- | --- |
| `templates/t_northwind/MSA-v7.docx` | the tenant's template, as written by the harness |
| `out/t_northwind/idem-2026-0042-nimbus/MSA-v7.pdf` | the merged document, before governance |
| `out/t_northwind/idem-2026-0042-nimbus/MSA-v7.governed.pdf` | after the compliance passes, unsigned |
| `out/t_northwind/idem-2026-0042-nimbus/MSA-v7.export.pdf` | the signed edition — the deliverable |
| `out/authority.p12` | the signing identity, created by the harness and used to seal the export |

## Notes

- **`pdfcraft-cli` must be on `PATH`.** PdfCraft takes `--root`, and the
  pipeline refuses any path outside it. WordCraft takes no root flags at
  all, so the bridge keeps its own path policy.
- **No key, no server, no network.** The signing identity is generated by
  the harness, so the pipeline runs end to end with nothing but the engines
  on `PATH`.
- **The signed PDF is not byte-stable across runs.** A signature embeds its
  own signing time, so two runs produce two different files. The pipeline
  reports the hash of the bytes it wrote, and the harness checks that
  report against the file on disk — not against a golden value.
- **`npx tsx`, not `node`.** The listings are TypeScript with `.js`
  specifiers; `tsx` resolves them.
- Type-check it with `npm run check` (which is `tsc --noEmit`).
